## Current / Issue

The user reports delayed add/restart actions and a current chat's visible × that has neither hover feedback nor a click response. The supplied screenshot shows the current transcript beside Traffic. It does not reveal which element receives the pointer or whether the renderer is blocked.

Confirmed avoidable work, with its duration unmeasured when this was written (later timings are in Status):

- `App.startIn` sets loading state, inserts the new session, changes workspace state and refreshes projects. Each App render renders every mounted `Session`; its inline activation/restart/continue callbacks change identity each time. A Session walks its messages and constructs transcript elements even when its conversation is unchanged. Entry bodies already have their own memoization.
- A conversations-changed push asks main for `activeSessions`. `unreadSince` reads, validates and parses matching event payloads only to take the array length. `pendingDecisions` asks for full `transcriptState`, then discards working/usage and all pending-request details except IDs. These synchronous SQLite and JavaScript operations run on Electron's main thread for each open conversation.
- `Session`'s diagnostic subscription depends on the whole props object, so a parent render replaces the subscription unnecessarily.

Root cause of the dead × remains unproven. A blocked renderer and pointer interception are different hypotheses. Previous source inspection found no disabled state, persistent capture path or confirmed drag-region overlap. The screenshot's cursor is a clue, not proof. Runtime traces came later, on synthetic data only; see U4 and Status.

Agent boot is a separate wait: new conversations return only after participants start. Health checks spawn version probes and also evaluate current provider preconditions. This plan preserves the awaited boot and evaluates preconditions on every health/start call. Only a successfully parsed version may be reused briefly under U3.

## Proposed

Remove the verified redundant work while retaining event-log ownership, chat lifecycle and readiness semantics. Keep this change confined to chat-list reads, the parent-to-Session render boundary and recent CLI version probes. Do not claim that these changes prove or resolve the dead × without observing the failing UI.

Before: chat action → App update → every mounted Session constructs its transcript; list refresh → decode unread event payloads and calculate full transcript state.

After: chat action → App update → unchanged session host skips rendering, affected chat updates normally; list refresh → count event rows and read pending IDs from existing projections. Participant startup reuses a recent or in-flight version probe while continuing to check provider preconditions.

## Code Changes

### U1 — Narrow chat-list reads

Files: `packages/event-store/src/store.ts`, its existing test file, and `apps/desktop/src/main/runtime.ts`. Independent of U2.

Add `EventStore.count(conversationId, options?: Pick<ReadOptions, 'afterSeq' | 'types'>): number`. Use `COUNT(*)` with the same conversation, exclusive sequence and type-filter semantics as `read`. Share the small WHERE/parameter construction between read and count to prevent drift. Undefined/empty types mean no type filter. No payload selection, validation or parsing; no ordering, paging, schema or index change. The restricted options prevent silently interpreting a read limit as an unbounded count.

Intended difference for corrupt legacy data: `read` parses and validates every event and can throw on a malformed payload; count only reads the row total. Listing an unread count therefore no longer fails because an otherwise matching row has an invalid payload. Full transcript reads retain their validation and error behavior.

Add an ID-only query over the existing approvals/questions projections. Return `{ pendingApprovalIds: string[]; pendingQuestionIds: string[] }`. Match transcriptState's unresolved predicates and created-at ordering exactly, including existing behavior for expired but unanswered requests. Do not add a second in-memory source of truth or change full transcriptState.

Route runtime's `unreadSince` and `pendingDecisions` through these methods. Other callers of those runtime helpers benefit without changing IPC responses.

Authored regression cases must compare counting with existing read semantics, exercise conversation isolation and exclusive boundaries, and compare pending IDs with full transcriptState across creation, resolution, cancellation and expiration where existing fixtures support them. Tests were authored unrun, then run by Codex once the user authorized focused tests.

The event-store package also exists as a copy in the Chorus repository. This local additive change does not authorize syncing, committing or publishing to that repository. No whole-file copies to another repository.

As implemented: a module-level `eventFilter(conversationId, options)` in `store.ts` builds the conversation, exclusive `afterSeq` and inlined `types` clauses and their parameters; `read` and the new `count` both use it, and `readPage` is untouched. `count` runs `SELECT COUNT(*) AS n FROM events WHERE …` with no ordering or limit. `pendingDecisionIds(conversationId)` selects only `id` from `approvals` where `outcome IS NULL` and from `questions` where `answered_at IS NULL`, each `ORDER BY created_at`, which are `transcriptState`'s exact predicates and order; `transcriptState` is unchanged. Runtime's `unreadSince` now calls `store.count` with the same `afterSeq` and `UNREAD_EVENT_TYPES`, and `pendingDecisions` returns `store.pendingDecisionIds`. A second benign difference besides malformed events: `transcriptState`'s usage query parsed usage payloads without a guard, so a malformed usage row used to make the pending-ID lookup throw; the ID-only read no longer touches it. Authored cases in `store.test.ts`: count against read across exclusive boundaries, type filters including an empty list and an unknown type, conversation isolation and a missing conversation, and a raw malformed row that `read` rejects and `count` counts; pending IDs in `created_at` order against `transcriptState`, an expired unresolved request, approvals decided, cancelled and withdrawn, questions answered and cancelled, isolation and a missing conversation. All passed in the focused run.

### U2 — Isolate unchanged chat renders

Files: `App.tsx`, `Session.tsx`, a small `SessionHost.tsx` and its focused component test. Depends only on the current Session prop contract.

Introduce one module-level memoized Session host. Derive its props from the existing Session component type where practical. It receives the existing session/carry/callback props plus pane ID and the stable `startIn` action. Construct activation, restart and continuation callbacks with useCallback and primitive project/conversation/pane dependencies. App renders this host instead of creating fresh callback props for Session. Move the existing `key={session.conversationId}` onto the host at the same tree position; preserve Session's carry-on-unmount and active-tab remount behavior.

Use ordinary shallow memoization. No custom comparator, long-lived callback map, remount key changes or ref-based concealment of props. The current conversations-changed handler preserves the SessionInfo objects of existing conversations; verify that remains true. A new session, changed session info, changed active state, settings/language change or carry change must still propagate. Session's own view/state and store subscriptions keep updating normally. One host boundary is sufficient; do not also memoize Session unless there is a demonstrated need.

Bind `const onActivate = props.onActivate` locally, invoke that local inside the diagnostic effect, and depend on `[conversationId, t, onActivate]` rather than all props. Preserve its current conversation and translation dependencies and behavior. This also avoids a method call bound to the whole props object.

Authored component coverage should count unrelated parent-driven renders, then exercise changed session info, active state, pane movement and a changed start action to detect stale callbacks. Verify the host forwards carry/registration props. Mocking the expensive Session body isolates the boundary; this does not verify real transcript layout or browser hit-testing.

As implemented: `SessionHost.tsx` exports `SessionHostProps`, which is `ComponentProps<typeof Session>` without `onActivate`, `onRestart` and `onContinue`, plus `paneId` and `startIn`, and `SessionHost`, one `memo` over a named function with default shallow comparison. It builds `onActivate` from `paneId` (calling `focusPane` on the store) and `onRestart`/`onContinue` from `startIn` and the session's `projectId` and `conversationId`, each with `useCallback`, and spreads every other prop onto `Session` unchanged. App's `renderSession` renders `<SessionHost key={session.conversationId} … paneId={paneId} startIn={startIn} />` in place of `<Session key={session.conversationId} …>`, passing the same session, active, carry, `onCarry`, `onDraftReader`, `onPromoteAside` and `explainLanguage`; App no longer imports the `Session` value. The two comments that explained the Restart and Continue arrows moved verbatim with them into `SessionHost`. In `Session.tsx`, `const onActivate = props.onActivate` sits above the diagnostic effect, which now calls it and depends on `[conversationId, t, onActivate]`; the two JSX capture handlers still read `props.onActivate`, and no other Session logic changed. `SessionHost.test.tsx` mocks `./Session.js` and `./workspace/store.js` and covers: an unchanged parent render does not render the chat again; changed session, active and carry render it again and arrive intact; the registration, promotion and language props arrive by identity while `paneId` and `startIn` do not; and after a pane move and a new start action, activate, restart and continue reach the current pane and action and never the previous one, and after the session's `conversationId` and `projectId` change on the same host, restart and continue start from the new ids. Fixtures are a complete typed `SessionInfo` and a complete `SessionCarry` seeded from `EMPTY_VIEW`, with no casts. Passed in the focused run.

### U3 — Reuse recent CLI version probes

Files: `packages/adapter-claude/src/claude-adapter.ts`, `packages/adapter-codex/src/codex-adapter.ts`, and focused adapter tests. Independent of U1/U2. Codex inspected both health and resolver paths; Claude assessed the bounded cache design after the initial whole-health cache was rejected.

Each adapter keeps at most one current version-probe entry, keyed by the actual executable file and ordered launch arguments after resolution. Share an in-flight probe for that key. Retain only successfully parsed versions for 30 seconds measured from probe completion with the existing injectable clock. A failure, timeout or unparseable response clears its entry so a later call can retry. An older probe finishing must not clear or replace a newer entry for a different key. A resolver that recovers to a new executable must force a new probe. No global cache, disk cache, exported test-only helper or new dependency.

Claude's provider precondition remains outside the version cache and runs separately on every health call, as well as the existing start check. Preserve launcher/SDK-path distinctions on Windows, version parsing and failure-message wording. Runtime's read-only profiling guard, awaited participant startup, resume and boot-failure behavior remain unchanged.

Intended bounded change: a CLI removed or replaced within the lifetime can still have a recent ready/version result. The actual startup still tries the CLI and reports its normal failure; another health call after expiry observes the changed install. Missing/invalid CLI results are never cached. This is version information, not cached authentication.

Author cases through the adapters' public health API with a fake clock and a mocked process probe: repeated success, concurrent coalescing, expiry at its boundary, failed/invalid probes retried, adapter isolation, resolver/key recovery, and Claude credential preconditions changing despite a cached version. Respect Node's custom promisify contract for execFile, whose promise returns stdout and stderr together. No public injection API solely for tests. Tests were authored unrun, then run by Codex once the user authorized focused tests.

As implemented, identically in `claude-adapter.ts` and `codex-adapter.ts`: a module constant `VERSION_PROBE_TTL_MS = 30_000`, a module type `VersionProbe` (`{ version }` or `{ reason }`) and `VersionProbeEntry` (`key`, `result`, `doneAt`), one private `latestProbe` field per adapter instance, and a private `probeVersion(file, args)`. The key is `JSON.stringify([file, ...args])` of what is actually spawned, computed after the existing resolver: for Claude the launch pair when one was resolved, otherwise `executablePath ?? command` (the Windows SDK path is never probed), for Codex `command` plus `commandArgs`. A matching entry is returned while in flight (`doneAt === null`); once complete, its age `now() - doneAt` is computed once and the entry is reused only when `age >= 0 && age < 30_000`, so a clock that moved back before the completion time forces a new probe (F1 correction; this guards negative age only and does not make the clock monotonic). Otherwise a new probe replaces it. The probe promise never rejects: it resolves to the parsed version, to `could not parse version from "…"`, or to the error's `message`, the same wording `health()` used before. A bookkeeping continuation registered before any caller awaits sets `doneAt = now()` on success or drops the entry on failure, and does nothing if a newer entry has already replaced it. `health()` keeps its `try`/`catch`; Claude still evaluates `precondition()` after the probe on every call, and `start()` still re-checks it. Bounded staleness: a CLI removed, replaced or upgraded within 30 seconds of a successful probe can still report its previous ready version; the session start then exercises the real CLI and fails or proceeds as before, and the next probe after expiry sees the change. Failed, timed-out and unparseable probes are never retained. Authored cases: `packages/adapter-claude/src/version-probe.test.ts` (reuse until 29,999 ms after completion and a new probe at 30,000, three concurrent calls sharing one probe, a rejection and an unreadable output each followed by a fresh probe, the precondition changing between calls with one probe, two adapters probing separately, a clock moved back to before the last completion forcing a new probe, and a resolver that fails and then recovers to a launch pair whose probe survives the older probe's failure) and `packages/adapter-codex/src/version-probe.test.ts` (the same timing, rewound-clock, sharing, failure and recovery cases with a `cmd.exe` launch prefix). Both mock `node:child_process` `execFile` through `Symbol.for('nodejs.util.promisify.custom')` so `run` resolves `{ stdout, stderr }`, and no real CLI is spawned. Passed in the focused run. Both adapter files were later edited by concurrent project-tool work (file times 18:19 for Claude, 18:53 for Codex); by diff against the baseline, `probeVersion` and `health()` are unchanged. Codex reran both probe suites on the current files: Claude 7 and Codex 5 passed. The current Codex adapter typecheck passed. The current Claude adapter typecheck reports two errors in the concurrent `project-tool.test.ts`, at lines 64 and 140, outside the version-probe change.

### U4 — Reuse timestamp formatters within a render batch

Two isolated synthetic runs reproduced a 106ms and a 100ms task after closing a chat and mounting its replacement transcript. The second CPU profile has 15 samples in that interval: approximately 45.9ms in `Clamped.measure` and 28.5ms in `EntryHead`. These coarse samples show cost but do not prove repeated layout thrashing. Claude challenged that attribution: the short fixture messages leave the clamp open, so the first measurement can account for the layout of newly inserted rows. Clamp changes are deferred.

Every timed `EntryHead` called `clockTime`, which constructed an `Intl.DateTimeFormat` for every message. U4 reuses each locale's formatter within one synchronous batch, then clears the cache in one queued microtask. This removes repeated construction while a transcript mounts. It does not keep a formatter across later tasks: ECMA-402 fixes a formatter's time zone when it is constructed ([CreateDateTimeFormat](https://tc39.es/ecma402/#sec-createdatetimeformat)), so a lifetime cache would keep showing the old zone after the system zone changed. A `Map<string | undefined, Intl.DateTimeFormat>` keeps the default locale apart from an invalid empty one. The options, output, exceptions and public signature were to stay unchanged. Only `format.ts`, its existing test file and this plan were in scope. Tests had to cover output, per-locale reuse, default and invalid locales, and refresh after the microtask. This targets the measured mount cost. It does not establish the dead control's cause or provider-start latency.

As implemented: a module-level `clockFormats = new Map<string | undefined, Intl.DateTimeFormat>()` sits above `clockTime`, whose JSDoc is unchanged. `clockTime` looks up its locale. On a miss it constructs the formatter with the same options, queues one microtask that clears the map if the map was empty, then stores the formatter. Construction runs before anything is queued or stored, so an invalid locale throws the same `RangeError` and nothing is kept for it. `undefined` and `''` are distinct keys, so the default locale is never confused with an invalid empty one. The signature, options and output are unchanged, and `resetMoment` is untouched. A formatter lives for at most one synchronous run, so the next task picks up a changed default time zone or locale. Under React's time-sliced (transition) rendering that run is one slice rather than a whole commit, so reuse is per slice there. Authored cases in a new `clockTime formatter reuse` block of `format.test.ts`: four timestamps format with one construction and match a fresh `Intl.DateTimeFormat`; en-US, en-GB and the default locale each construct once and keep their own output on reuse; a later task constructs again; and an empty locale throws `RangeError` on every call without being stored, after which en-GB still constructs. Reference formatters are built before the constructor spy, and each case first awaits a macrotask so an earlier batch's clear has run. The three existing `clockTime` cases are unchanged. Codex found no production defect, and ESLint and Prettier passed on `format.ts`, `format.test.ts` and this plan. Codex's first focused run passed the 14 existing cases and failed all four new ones with `TypeError: format.format is not a function`. Vitest 4.1.10's default constructor spy calls `Reflect.construct(original, args, mock)`, so the native constructor built its object on the mock's prototype, which has no `format`. The correction captures `Intl.DateTimeFormat` before any spy and gives each spy a plain-function implementation returning `new NativeDateTimeFormat(...args)`. Construction counts, locale cases, the invalid-locale case, the microtask case, reference construction outside the spy and `afterEach` restoration are unchanged. Codex's rerun then passed all 18 formatter cases, and ESLint and Prettier passed again. Only `Entry.tsx` calls `clockTime` in production, always with the default locale.

Paired measurement, run by Codex. Concurrent edits had changed other renderer files since the saved pre-U4 snapshot, so comparing whole old and new bundles would have mixed those changes in. Instead the current built renderer was copied twice. In the baseline copy, only `clockTime` was replaced with its compiled pre-U4 function, and the unused cache declaration was removed. Both copies got the same private hook exposing the real workspace store. The repository's build output and source were not touched.
